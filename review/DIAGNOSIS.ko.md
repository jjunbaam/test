# GitLab QA Analyzer 구현 진단

## 판단

포털 전체를 버릴 필요는 없지만, **분석 핵심은 재설계·교체가 필요하다.** 현재는 커밋 diff 일부, 파일명 검색, 불완전한 화면 매핑을 AI 또는 고정 문구에 전달하는 시제품이다. 목표인 “Branch 변경을 최신 PR/R에 반영할 때 영향을 받는 실제 화면·기능과 수동 검증 절차”를 뒷받침하는 버전 비교와 증거 연결이 없다. 프롬프트 변경이나 Sourcegraph 연결만으로 해결되지 않는다.

이 판단은 제공된 ZIP의 구현과 외부 통신을 차단한 재현 검증에 근거한다. 실제 사내 GitLab/Sourcegraph 연결, 배포 상태, DLPCenter 코드의 실제 영향 화면은 검증하지 않았다. 이전 모델의 작업 과정이나 의도는 판단할 수 없다.

## 재현 결과

`review/reproduce_findings.py`는 실제 GitLab/Sourcegraph/AI 호출을 하지 않는 결함 재현 코드다. 7개 검사 모두 예상한 문제를 재현했다. 이는 제품 품질 테스트가 통과했다는 뜻이 아니다.

1. 외부 연결을 검사하지 않아도 첫 화면에 `Sourcegraph Live API Connected`가 표시됨.
2. 첨부 매핑 파일이 존재하지만 Linux에서 `URL_MAP`이 빈 사전으로 로드됨.
3. PR/R 요청이 동일한 GitLab URL만 조회하며, Pi 실패를 주입해도 성공 및 동일한 사이드이펙트 결과를 반환함.
4. Java 주석 변경만으로 HIGH 및 500 에러 위험을 생성함.
5. 두 화면 후보를 응답해도 첫 화면만 반환하고 선택 커밋 SHA는 검색에서 빠짐.
6. 25파일 응답 중 20개만 분석 대상으로 남기고 각 diff를 자름.
7. 매핑 97개 중 57개가 일반 컨트롤러 이름임을 확인함.

실행: 저장소 루트에서 `python -m unittest discover -s review -p reproduce_findings.py -v`.
필요 패키지: requests, urllib3, uvicorn, starlette, httpx. 이번 실행은 Python 3.12 및 임시 설치 경로를 사용했다. 실제 서비스 통합·브라우저 시각 검증·AI 응답 품질 검증은 미실행이다. 2번 검사는 원본의 Windows 경로가 없는 환경에서 재현된다.

## Sourcegraph 연동에 대한 정확한 결론

연동 코드 자체는 존재한다. 매핑에 없는 Java 파일에 대해 GraphQL 검색을 호출한다. 따라서 “전혀 연동하지 않았다”고 단정할 수 없다. 다만 연결 상태 확인, 실패 표시, 특정 버전 고정, 메서드 수준 의존성 증거, 여러 화면 추적이 부족하다. 정적 매핑에 있는 파일은 Sourcegraph를 호출하지 않고도 결과에 Sourcegraph 팩트라는 표현을 사용한다. 실제 서버가 정상 응답했는지는 별도 런타임 기록이 필요하다.

## 재사용과 교체 권고

- 재사용 후보: 커밋 선택 UI, 결과 카드와 TC 표, Markdown 내보내기 구성, GitLab API 호출의 기본 형태. 오류 처리와 정확성 검증은 다시 필요하다.
- 참고자료로만 유지: 기존 URL 매핑. 실제 메뉴·라우트·권한·버전 정보를 대조해 검증해야 한다.
- 교체 필요: PR/R 비교, 코드→화면 추적, 영향 판정, AI 입력 증거 구성, 실패/불확실성 처리, 검증 결과 데이터 구조.
- 과거 패치용 스크립트는 반복 실행하지 않는다. 문자열 치환으로 app.py를 덮어쓰며 현재 구현과 일치하는지 보장되지 않는다.

## 권장하는 다음 설계

1. 선택 커밋과 부모, 최신 PR/R의 정확한 SHA를 각각 기록한다. Branch 전체 병합인지 선택 커밋 cherry-pick인지 먼저 정의하고, 각 대상 코드에 변경을 적용했을 때의 실제 차이·충돌·이미 반영된 변경을 구분한다. 단순 Branch 대 PR diff로 다른 개발 전체를 섞지 않는다.
2. 실제 메뉴/화면 목록을 확보한다. 화면 ID, 한글 메뉴 경로, URL, 사용 권한, 버튼·기능, 호출 API, 코드 버전을 연결한다. 라우팅·JSP·JS·메뉴 설정과 기존 QA 문서를 근거로 삼고 미확인 항목은 표시한다.
3. 변경 메서드/SQL → 호출자 → Controller/API → JSP/JS 이벤트 → 실제 메뉴를 추적한다. Sourcegraph는 증거 검색 도구로 활용하며 검색 결과를 호출 관계로 곧바로 단정하지 않는다. 여러 화면과 공통 모듈 영향도 보존한다.
4. AI에는 확인된 증거와 변경 전후 조건만 전달한다. 실제 화면, 영향 가능성이 있는 기능, 전제조건, 조작 절차, 기대 결과, 근거 위치, 불확실성을 출력한다. 화면을 못 찾으면 “미확인”으로 남기며 메뉴명을 창작하지 않는다. 영향 경로가 있다는 것과 결함이 발생한다는 것은 구분한다.
5. 분석 결과를 대상 SHA와 함께 저장한다. 반영 후 실제 배포 SHA를 확인하고 QA의 통과/실패/미실행 결과를 연결한다. 현재 구현에는 이러한 결과 관리가 없다.
6. 알려진 과거 결함 사례와 영향 없는 변경을 함께 평가한다. 화면 적중률, 누락, 근거 없는 화면 생성, 검증 절차의 실행 가능성을 측정한 뒤 범위를 넓힌다. README의 “테스트 60% 감소”는 첨부 자료에서 검증 근거를 확인할 수 없다.

## GitHub 업로드 처리와 보안

- 원본 ZIP은 Git에 포함하지 않는다. `__pycache__`의 컴파일 파일도 토큰 잔존 가능성이 있어 제외한다.
- app.py의 GitLab/Sourcegraph 토큰과 build_url_map.py의 GitLab 토큰을 환경변수 `GITLAB_TOKEN`, `SOURCEGRAPH_TOKEN` 참조로 대체했다. 토큰 값은 문서와 커밋에 기록하지 않는다. 노출된 원본 토큰은 폐기·재발급이 필요하다.
- .gitignore와 이 진단 문서/재현 코드를 추가했다. 분석 기능은 수정하지 않았다.
- 원본은 TLS 검증을 끄고, Sourcegraph HTTP를 사용하며, 인증 없는 코멘트 쓰기 API와 광범위 CORS 및 debug 모드가 있다. 운영 전에 수정해야 한다. 이번 검토에서는 실 토큰 사용·실 서비스 호출·GitLab 코멘트 작성을 하지 않았다.

## 후속 구현 전에 필요한 자료

실제 DLPCenter 메뉴·라우트·관련 소스의 허용된 접근 방식, Branch/PR/R의 실제 저장소·ref 관계와 반영 방식, 기대 영향 화면이 알려진 대표 커밋 및 실제 오답 리포트가 필요하다. 비밀값은 채팅이나 Git에 넣지 않는다. 이 자료 없이 실제 화면 정확도나 Sourcegraph 운영 상태를 확인했다고 주장할 수 없다.
